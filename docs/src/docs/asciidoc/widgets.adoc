----

----

Wrap modes, set with `.overflow(...)` (CSS property: `text-overflow`):

* `Overflow.CLIP` - No wrapping, text is clipped
* `Overflow.WRAP_CHARACTER` - Wrap at any character
* `Overflow.WRAP_WORD` - Wrap at word boundaries
* `Overflow.ELLIPSIS` / `ELLIPSIS_START` / `ELLIPSIS_MIDDLE` - Truncate with `...` at the end, start, or middle

With a wrap mode, a wrapped line continues under its first non-blank character instead of at the left edge, so an
indented line (a list entry, a key and its value) keeps its indent when it wraps. An indent that leaves no room for
text falls back to the left edge.

==== ListWidget vs ListElement

TamboUI provides two list implementations at different API levels:

[cols="1,2,2",options="header"]
|===
|Feature |ListWidget (widgets layer) |ListElement (toolkit layer)

|State management
|External `ListState` required
|Internal state, no external state needed

|Item types
|`ListItem` only (text + style)
|Any `StyledElement` (text, rows, panels, etc.)

|Usage
|Direct widget rendering
|Toolkit DSL fluent API

|Best for
|Custom TuiRunner apps, fine-grained control
|ToolkitApp, declarative UIs
|===

**ListWidget** is for low-level control when you need to manage state externally or are building custom rendering with `TuiRunner`.

**ListElement** is for Toolkit DSL users who want:

* Internal state management (no `ListState` needed)
* Rich content (any `StyledElement` as items, not just text)
* Automatic event handling (UP/DOWN navigation built-in)
* Seamless integration with other toolkit elements

==== Out-of-range and missing points

A point outside the axis range has no marker, but a line through it still runs to the edge of the
chart — the line is clipped at the edge, not dropped.

A point with a `NaN` or infinite coordinate is skipped and breaks the line at that spot, so a missing
value shows as a gap rather than the line falling to zero.

==== CSS Properties

Spinner style and frames can be configured via CSS:

[source,css]
----
/* Use a predefined style */
.loading-spinner {
    spinner-style: line;
    color: cyan;
}

/* Use custom animation frames */
.custom-spinner {
    spinner-frames: "⠋" "⠙" "⠹" "⠸" "⠼" "⠴" "⠦" "⠧";
}

/* spinner-frames overrides spinner-style when both are set */
.fancy-spinner {
    spinner-style: dots;
    spinner-frames: "*" "+" "x" "+";  /* This takes precedence */
}
----

NOTE: Programmatic styles set via `spinnerStyle()`, `frameSet()`, or `frames()` take precedence over CSS styles.

NOTE: **For Toolkit DSL users**: Use `SpinnerElement` via `spinner()` factory methods. It manages state internally and advances automatically on each render. See <<toolkit-dsl>>.

State methods:

* `state.text()` - Get full text content
* `state.setText(text)` - Set text content
* `state.lineCount()` - Get number of lines
* `state.getLine(row)` - Get text of specific line
* `state.insert(char)` / `state.insert(string)` - Insert at cursor
* `state.deleteBackward()` / `state.deleteForward()` - Delete characters
* `state.moveCursorUp()` / `moveCursorDown()` / `moveCursorLeft()` / `moveCursorRight()` - Move cursor
* `state.moveCursorToLineStart()` / `moveCursorToLineEnd()` - Jump to line boundaries
* `state.moveCursorToStart()` / `moveCursorToEnd()` - Jump to document boundaries
* `state.scrollUp(amount)` / `state.scrollDown(amount, visibleRows)` - Manual scrolling
  (`scrollDown(amount, visibleRows, visibleCols, overflow)` counts wrapped rows when wrapping)
* `state.clear()` - Clear all content

Wrap modes:

By default a long line is clipped and the view scrolls horizontally. Set `.overflow(...)` on
`TextArea.Builder` (or `.overflow(...)` / `.wrapWord()` / `.wrapCharacter()` / `.clip()` on
`TextAreaElement`) to wrap it across multiple screen rows instead:

* `Overflow.CLIP` - No wrapping, horizontal scrolling (default)
* `Overflow.WRAP_CHARACTER` - Wrap at any character
* `Overflow.WRAP_WORD` - Wrap at word boundaries

While wrapping, `Up`/`Down` move the cursor by visual row rather than by logical line, keeping
its screen column, and the line-number gutter shows a number only on the first row of each
logical line. A line whose last row fills the whole width is followed by an empty row, so the
cursor at the end of that line stays visible. In the Toolkit DSL, a wrapping `TextAreaElement`
asks its container for enough rows to show every wrapped line.

NOTE: Unlike `Paragraph`, a text area does not support the truncating modes (`Overflow.ELLIPSIS`,
`ELLIPSIS_START`, `ELLIPSIS_MIDDLE`) - the cursor can move into text they would hide. They fall
back to `Overflow.CLIP`.

CSS properties:

* `cursor-color` - Cursor highlight color
* `placeholder-color` - Placeholder text color
* `line-number-color` - Line number gutter color
* `text-overflow` - Wrap mode (`clip`, `wrap-word`, `wrap-character`)

[[syntax-highlighting]]
=== Syntax Highlighting

A reusable component for coloring source-code tokens, independent of any single
widget. It lives in `dev.tamboui.widgets.syntax` and is consumed by
`MarkdownView` for fenced code blocks, but any code/editor widget can reuse it.

* `SyntaxHighlighter` — the component interface
  (`List<Line> highlight(String code, String language, Style base, SyntaxTheme)`).
  Implement your own for a custom tokenizer, or use `SyntaxHighlighter.none()`
  to disable highlighting.
* `RegexSyntaxHighlighter` — the built-in regex tokenizer (highlight.js-inspired)
  with grammars for `java`, `kotlin`, `javascript`, `typescript`, `python`,
  `json`, `xml`/`html`, `css`, `bash`, `yaml`, `properties`, `sql`, `go` and
  `rust`.
* `Grammar` — a declarative language definition: an id, aliases, and rules
  (`pattern`, `literal`, `multiline`).
* `SyntaxTheme` — maps a `TokenType` to a `Style`; `SyntaxTheme.DEFAULTS` is a
  light-on-dark palette. `builder()` starts with that palette; use `token()` to
  replace entries or `clear()` to make tokens inherit the enclosing style.

[source,java]
----
import java.util.List;

import dev.tamboui.widgets.syntax.RegexSyntaxHighlighter;
import dev.tamboui.widgets.syntax.SyntaxHighlighter;
import dev.tamboui.widgets.syntax.SyntaxTheme;
import dev.tamboui.widgets.syntax.TokenType;
import dev.tamboui.style.Color;
import dev.tamboui.style.Style;

SyntaxHighlighter highlighter = RegexSyntaxHighlighter.defaults();
SyntaxTheme theme = SyntaxTheme.builder()
    .token(TokenType.KEYWORD, Style.EMPTY.bold().fg(Color.rgb(198, 120, 221)))
    .build();

List<Line> lines = highlighter.highlight("int x = 1;", "java", Style.EMPTY, theme);
----

Renders CommonMark + GFM markdown to a buffer. Lives in its own

[[world-map]]
=== WorldMap

`WorldMap` is a stateless, offline `Widget` built on `Canvas`. It bundles a Natural
Earth 1:50m coastline (about 247 KB) and adds no runtime libraries, no network access
and no setup. It uses the Braille rasterizer (2 by 4 dots per cell).

[source,java]
----
WorldMap map = WorldMap.builder()
    .viewport(new MapViewport(-6, 16, 44, 58))   // west, east, south, north
    .tint(Color.rgb(12, 28, 54), Color.rgb(34, 92, 48))  // sea, land
    .coastlineColor(Color.rgb(140, 200, 255))
    .route(new RouteShape(new double[][] {{10.49, 55.28}, {-1.55, 47.22}}, Color.MAGENTA))
    .marker(new MapMarker(10.49, 55.28, Color.YELLOW, "Pederstrup"))
    .build();
map.render(area, buffer);
----

Coordinates are longitude, latitude in degrees, in that order. The default viewport is
the whole world. For an antimeridian crossing, use unwrapped bounds such as
`new MapViewport(170, 190, -20, 20)`.

==== Projection and aspect ratio

Coordinates use an equirectangular (plate carrée) projection. Rather than stretching to
fill the rectangle, the viewport is expanded on its shorter axis to match the rectangle's
proportions (correcting for a terminal cell being about twice as tall as wide), so the map
fills the area without distortion and shows a little more geography. The whole globe is the
one case that cannot fill a non-4:1 rectangle, so it letterboxes. This is plate carrée, not
Mercator: it is for overviews, not local navigation, and it does not align with Web Mercator
map tiles. All geographic transforms go through `GeoProjection`, which also converts screen
positions back to coordinates for hit-testing and pan/zoom.

==== Layers

`WorldMap` composes a small set of layers in a fixed order. They split across two rendering
planes: a raster plane (cell backgrounds) drawn first, then a vector plane (Canvas foreground).

[cols="1,1,3",options="header"]
|===
|Layer |Plane |Notes
|`tint(water, land)` |raster |Smooth land/sea shading in cell backgrounds, supersampled and blurred for soft coasts. The prettier land option.
|`landColor(color)` |vector |Braille land fill (`LandShape`). The cheap foreground alternative to `tint`.
|`region(RegionShape)` |vector |Filled and/or outlined polygon (scanline fill); draw order below the coastline.
|coastline |vector |`CoastlineShape`, always Braille.
|`route(RouteShape)` |vector |Geographic polyline; wraps across the antimeridian.
|markers |overlay |One-cell `●` dot with an optional name, clipped to the widget's right edge.
|===

Markers outside the viewport are culled; later markers win in the same cell. A marker's
optional label is drawn beside the dot and clipped (on a grapheme boundary) to the widget
border, so whatever fits is shown. The widget clears its rectangle each render. Compose a
`Block` around it for borders.

==== Interaction

The toolkit `WorldMapElement` (via `Toolkit.worldMap(...)`) holds a mutable `MapState` (the
viewport) and adds keyboard and mouse control, delegating rendering to the stateless `WorldMap`.
`MapState` is the map counterpart of `ListState`/`TreeState`: supply one with `.state(mapState)`
so the viewport survives element rebuilds and application code can mutate it (for example a search
flying to a result) or read it to react to panning.

Controls:

- arrow keys or `h j k l` pan (a fixed fraction of the view),
- `+` / `-` zoom, `0` resets to the whole world,
- `r` toggles land shading,
- the mouse wheel zooms toward the cursor, and dragging with the left button pans.

Panning normalizes longitude across the antimeridian and clamps latitude to the poles; at
full zoom-out, horizontal panning rotates the centered longitude (all of this lives in
`MapState`, so it is unit-testable without the toolkit). Run `./run-demo.sh worldmap-demo` to try it.

==== Composing in a Canvas

The layers are reusable `Shape` and raster primitives, so a map can share a Canvas with
your own routes, points, regions or labels. Configure the Canvas with the bounds you want to
see; shapes clip to those bounds (`Line` clips since
https://github.com/tamboui/tamboui/pull/526[PR #526]).

[source,java]
----
Canvas canvas = Canvas.builder()
    .xBounds(-20, 40).yBounds(30, 70).marker(Marker.BRAILLE)
    .paint(ctx -> {
        ctx.draw(new LandShape(Color.rgb(0, 60, 0)));      // bundled land fill
        ctx.draw(new CoastlineShape(Color.CYAN));           // bundled coastline
        ctx.draw(new RouteShape(new double[][] {{0, 50}, {20, 60}}, Color.RED));
        ctx.draw(new Points(new double[][] {{10.49, 55.28}}, Color.YELLOW));
    }).build();
----

The bundled geometry is Natural Earth 1:50m. To show finer or custom coastlines without bloating
the jar, pass a `CoastlineData` to `WorldMap.builder().coastlineData(...)` (or to `CoastlineShape`
and `LandShape` directly). Build it from your own polylines with `CoastlineData.of(double[][])` —
for example a higher-resolution Natural Earth export converted to longitude/latitude pairs. The
bundled binary resource is regenerated with the maintainer tool `config/generate-coastlines.java`
(run with JBang); its format is internal, not public API.

`CoastlineShape`, `LandShape`, `RouteShape` and `RegionShape` read their clipping bounds from
the Canvas. They take the shorter way around the globe and repeat across the seam, so a
seam-crossing viewport draws continuously. Generic Canvas shapes (`Points`, `Line`) use Canvas
coordinates directly and do not inherit this wrapping; supply unwrapped longitudes for them
when crossing the antimeridian.

==== Extension boundary

The base `WorldMap` must keep working with no GIS, image, HTTP, `java.awt` or geocoding
libraries, offline and dependency-free. Richer data (higher-resolution or custom coastline,
country and lake polygons), raster/satellite tiles (via `tamboui-image` protocols), level-of-detail
fetching while zooming, and geocoding/search are optional providers layered on top: they do
async work off the render thread and deliver results by updating the element's viewport state.
Map tiles are Web Mercator and would require a Mercator projection mode, which plugs in behind
`GeoProjection` without changing the layer code.
