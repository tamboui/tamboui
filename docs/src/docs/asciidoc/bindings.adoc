=== Prefer Semantic Predicates

Reach for the semantic predicates on `KeyEvent` instead of comparing `event.code()` to a `KeyCode`.

[source,java]
----
// Prefer this:
if (event.isUp()) { ... }
if (event.isConfirm()) { ... }
if (event.isDeleteBackward()) { ... }

// Over this:
if (event.code() == KeyCode.UP) { ... }
if (event.code() == KeyCode.ENTER) { ... }
if (event.code() == KeyCode.BACKSPACE) { ... }
----

A raw `event.code() == KeyCode.UP` check has three problems the predicates avoid:

* It matches **any** modifier combination (Ctrl+Up, Alt+Up), which is usually not what you want.
* It ignores the bindings, so it never picks up keypad variants, vim keys (`k`), emacs chords (`Ctrl+p`), or a user's custom binding set.
* It does not filter release events; the predicates do (via `KeyTrigger`), so a key is not acted on twice.

The available predicates, each matching its action in the current bindings:
`isUp()`, `isDown()`, `isLeft()`, `isRight()`, `isPageUp()`, `isPageDown()`, `isHome()`, `isEnd()`,
`isSelect()`, `isConfirm()`, `isCancel()`, `isQuit()`, `isFocusNext()`, `isFocusPrevious()`,
`isDeleteBackward()` and `isDeleteForward()`.

For text fields, use `isTyping()` to decide whether to insert a character: it is true for a typed
character (including keypad digits, IME and emoji text, and AltGr combinations) and false for
shortcuts and control keys, so you never insert the letter of a `Ctrl` chord. The
`dev.tamboui.tui.event.TextEditing` helper applies all of this (typing, editing and paste) to a
`TextInputState` or `TextAreaState` for you.

[NOTE]
====
Comparing `event.code()` directly - or the equivalent `event.isKey(KeyCode.UP)` - is only right when
you specifically want the *physical* key regardless of the bindings, which is rare. An example is
moving a floating panel with the arrow keys (spatial movement, where Shift+Arrow is meaningful and
`hjkl` should not apply); there, `event.isKey(KeyCode.UP)` is the honest choice.
====

For applications calling `EventParser.readEvent(...)` directly, a read timeout returns `null`, while terminal EOF throws the JDK's `EOFException` (a subclass of `IOException`). Once a bracketed paste starts, its content is read until the end marker even across read timeouts; a partial paste is never emitted just because input pauses. EOF during a paste discards its content. If an end marker never arrives, input waits in paste mode until EOF or application shutdown rather than interpreting a late pasted Enter as a key. Paste content is buffered as a single string with no fixed size limit, so memory use grows with the paste until it completes. `TuiRunner` and `InlineTuiRunner` stop their input reader on EOF.

=== Keyboard Protocol and Terminal Compatibility

{project-name} enables the **Kitty Keyboard Protocol** (`CSI u` / progressive keyboard enhancement) by default, in `AUTO` mode.
On terminals that implement it (Kitty, Ghostty, foot, WezTerm, recent Alacritty, and tmux `3.x` passthrough, among others) keys are reported unambiguously:

* **Ctrl+letter** keeps its case - Ctrl+a and Ctrl+Shift+A are distinct.
* **Tab vs Ctrl+I**, **Enter vs Ctrl+M**, and **Escape vs Alt combinations** are disambiguated.
* **Shortcuts match across keyboard layouts** (Cyrillic, AZERTY, Dvorak, ...) via base-layout key reporting.

For these terminals the historical control-key limitations below do **not** apply, and you can bind `Ctrl+key` combinations freely.

==== Protocol Modes

The mode is configured on `TuiConfig` or `InlineTuiConfig` via `KeyboardProtocol` (`AUTO`, `FULL`, or `LEGACY`).
See link:api-levels.html#_keyboard_protocol[API Levels -> Keyboard Protocol] for the full mode/flags reference and how the protocol stack is pushed and popped.

==== Legacy Terminal Fallback

[IMPORTANT]
====
On terminals that do **not** implement the Kitty protocol - or when you explicitly select `KeyboardProtocol.LEGACY` - input falls back to classic VT encoding, which has significant limitations.

When you press a key combination like Ctrl+A, a legacy terminal does not send "Ctrl" + "A" separately.
Instead, it sends a single ASCII control character (byte value 1 for Ctrl+A).
This encoding dates back to the 1970s and causes several problems:

* **Ctrl+letter (a-z)**: Works, but case information is lost. Ctrl+a and Ctrl+Shift+A send the same byte.
* **Ctrl+number**: Unreliable. Ctrl+2, Ctrl+@, and Ctrl+Space all send the same byte (0). The original key cannot be determined.
* **Ctrl+Alt+key**: Inconsistent across terminals.

**Alt key bindings are more reliable** in legacy mode because terminals send ESC followed by the actual character:

* Alt+a sends `ESC` + `'a'` - we know it was lowercase 'a'
* Alt+A sends `ESC` + `'A'` - we know it was uppercase 'A' (shifted)
* Alt+2 sends `ESC` + `'2'` - we know it was '2'
====

**If you need to support legacy terminals as well**, choose custom bindings that degrade gracefully:

[cols="1,1,2",options="header"]
|===
|Modifier |Legacy reliability |Notes

|`Alt+letter`
|Excellent
|Preserves case, works consistently

|`Alt+number`
|Excellent
|Fully distinguishable

|`Ctrl+letter`
|Good
|Works but loses shift information in legacy mode

|`Ctrl+number`
|Poor
|Avoid - ambiguous with other combinations in legacy mode
|===

With the Kitty protocol active (the default), all of these combinations are fully distinguishable.
For the widest reach, prefer `Alt+key` bindings for custom actions and reserve bare `Ctrl+key` for well-established conventions (Ctrl+C, Ctrl+S, Ctrl+Z, etc.).

==== Rich Event Model

With Kitty protocol support enabled, key events provide rich metadata:

* **Event Kinds**: `KeyEventKind.PRESS`, `KeyEventKind.REPEAT`, and `KeyEventKind.RELEASE`.
  Existing widgets and `KeyTrigger` bindings ignore `RELEASE` events by default to maintain full backward compatibility. You can match release events explicitly using `KeyTrigger.withKind(KeyEventKind.RELEASE)`.
* **Extended Modifiers**: In addition to Shift, Ctrl, and Alt, `KeyModifiers` supports `superKey` (Command / Windows key), `hyper`, and `meta`.
  Helpers such as `event.hasSuper()`, `KeyTrigger.superKey('k')`, and `KeyTrigger.withSuper()` are provided.
* **Special, Keypad, and Media Keys**: First-class support for `F13`–`F35`, numeric keypad keys (`KP_0`–`KP_9`, `KP_ENTER`, `KP_ADD`, etc. with `event.isKeypad()`), lock keys (`CAPS_LOCK`, `NUM_LOCK`, `SCROLL_LOCK`), and media keys.
* **Alternate Keys & Layout Independence**: Terminals report `event.keyCodePoint()`, `event.shiftedKeyCodePoint()`, and `event.baseLayoutKeyCodePoint()` (standard PC-101 layout), allowing shortcuts to match regardless of international keyboard layouts (like Cyrillic, AZERTY, or Dvorak).
* **Associated Text**: `event.text()` conveys the exact Unicode text generated by the key event (including combining characters and IME input).

=== Annotation Processing

By default, `@OnAction` methods are discovered at runtime using reflection.
For better startup performance and GraalVM native image compatibility, use the annotation processor to generate action handler registrations at compile time.

==== Gradle (Kotlin DSL)

[source,kotlin,subs="+attributes"]
----
dependencies {
    implementation("{maven-group}:{toolkit-module}:{project-version}")
    annotationProcessor("{maven-group}:{processor-module}:{project-version}")
}
----

==== Gradle (Groovy DSL)

[source,groovy,subs="+attributes"]
----
dependencies {
    implementation '{maven-group}:{toolkit-module}:{project-version}'
    annotationProcessor '{maven-group}:{processor-module}:{project-version}'
}
----

==== Maven

[source,xml,subs="+attributes"]
----
<dependencies>
    <dependency>
        <groupId>{maven-group}</groupId>
        <artifactId>{toolkit-module}</artifactId>
        <version>{project-version}</version>
    </dependency>
</dependencies>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.13.0</version>
            <configuration>
                <annotationProcessorPaths>
                    <path>
                        <groupId>{maven-group}</groupId>
                        <artifactId>{processor-module}</artifactId>
                        <version>{project-version}</version>
                    </path>
                </annotationProcessorPaths>
            </configuration>
        </plugin>
    </plugins>
</build>
----

The processor generates a `_ActionHandlerRegistrar` class for each component with `@OnAction` methods.
These registrars are discovered via `ServiceLoader` and register action handlers without reflection.

Property file format:

[source,properties]
----
# Navigation
moveUp = Up, k
moveDown = Down, j
pageUp = PageUp, Ctrl+u
pageDown = PageDown, Ctrl+d

# Actions
select = Enter, Space
cancel = Escape
delete = d, Delete

# Mouse
click = Mouse.Left.Press
contextMenu = Mouse.Right.Press
----

Multiple triggers for the same action are comma-separated.
Modifiers use `Ctrl+`, `Alt+`, `Shift+` prefixes.
